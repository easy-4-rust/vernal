# spring-beans → vernal-beans 全量迁移路线图

> 版本：v1.0（2026-07-27）｜基线：Spring Framework **7.0.8**（spring-beans）
> 参考实现：tx_di（Rust DI 实证项目，Gitee: `tian_xiong/tx_di`）
> 仓库：easy-4-rust/vernal @ dev ｜ 本文档随代码同步维护，每阶段完成时更新

## 一、总目标

以 Spring Framework 7.0.8 的 `spring-beans` 模块与 `tx_di` Rust DI 项目为双蓝本，
实现功能语义完全对齐的 `vernal-beans` crate。目标是让 Spring 用户的 Bean 编程模型
与 tx_di 用户的类型驱动 IoC 模型，在 vernal-beans 上**统一为同一套 API 表面**。

### 设计原则

1. **功能语义对齐，实现方式 Rust 化**：Java 反射 → trait 对象；Java 字节码 → 编译期宏；Java ClassLoader → 模块路径
2. **每个 .rs 文件只对应一个 Java 类或一个 tx_di 概念对象**，对齐 spring-beans 一个类一个文件的结构
3. **所有公开类型必须有中文文档注释**：结构体、枚举、trait、方法、字段
4. **模块路径 snake_case**，类型 PascalCase，方法 snake_case
5. **深度集成 vernal 生态**：`Container` 可作为 `vernal-context::ApplicationContext` 的实例缓存后端；`Component` trait 可由 `vernal-macros` 自动派生
6. **类型驱动优先**：保留 tx_di 的 `#[derive(Component)]` + associated type `Deps` 的强类型范式作为内核语义
7. **不实现字节码编译、BeanFactoryPostProcessor 的全局钩子**：Rust 编译期宏已覆盖该能力，仅保留基于 trait 的可扩展点
8. **Scope 状态机**：完整移植 spring-beans 的 `singleton / prototype / request / session / application` 模型，但自定义作用域由 Rust 标记类型驱动（vernal-beans 现状已有）

```rust
/// 对应 Java `org.springframework.beans.factory.BeanFactory`。
///
/// 提供按类型 / 按名称 / 按别名获取 Bean 实例的能力。
/// 该 trait 是访问 Spring 风格 IoC 容器的基础接口。
pub trait BeanFactory {
    /// 按完整组件标识获取实例。
    fn get_bean(&self, key: &ComponentKey) -> Result<Arc<dyn Any + Send + Sync>, BeanFactoryError>;

    /// 按类型获取唯一实例。
    fn get_bean_by_type<T: Any + Send + Sync>(&self) -> Result<Arc<T>, BeanFactoryError>;

    /// 按 ComponentProvider 暴露多实例能力。
    fn bean_provider<T: Any + Send + Sync>(&self) -> Box<dyn ObjectProvider<T>>;

    /// 检查容器是否包含指定组件。
    fn contains_bean(&self, key: &ComponentKey) -> bool;

    /// 返回所有别名。
    fn aliases(&self, key: &ComponentKey) -> Vec<Arc<str>>;
}
```

**验收**：所有现有 trait 全部保留，并新增 5+ 顶层接口 trait

## 四、工程规范

### 命名规则

| 项目 | 规范 |
|------|------|
| 目录/文件名 | snake_case（`bean_factory.rs`、`custom_editor.rs`） |
| 类型名 | PascalCase（`BeanFactory`、`CustomEditor`） |
| 方法名 | snake_case（`get_bean`、`is_singleton`） |
| 参数名 | 与 Java 字段名对齐（`bean_name`、`bean_class_name`） |

### 文件结构规范

```rust
//! 对应 Java 类：org.springframework.beans.factory.config.BeanDefinition
//! 对应 tx_di 模块：`tx-di-core/src/lifecycle.rs` 的 `Component`
//!
//! 描述一个 Bean 实例的元数据，包括属性值、构造参数和
//! 工厂方法等。接口最小化以允许 `BeanFactoryPostProcessor` 读取
//! 并修改属性值。

/// Bean 定义 trait — Spring 风格的 IoC 注册入口。
///
/// 对应 Spring 的 `BeanDefinition`；每条 `RegistryBuilder::register()` 都
/// 会把一个实现该 trait 的类型转换为不可变 [`ComponentDefinition`]。
pub trait BeanDefinition: Send + Sync + 'static {
    /// Bean 名称（唯一标识的一部分）。
    fn bean_name(&self) -> &ComponentKey;

    /// Bean 类型名。
    fn bean_class_name(&self) -> &str;

    /// 作用域。
    fn scope(&self) -> Scope;

    /// 是否惰性初始化。
    fn is_lazy_init(&self) -> bool;

    /// 是否 primary。
    fn is_primary(&self) -> bool;
}
```

### 测试规范

- 每个 trait 至少 1 个实现测试 + 1 个 mock 测试
- 每个错误类型至少 1 个构造 + 1 个 Display 测试
- Aware 体系通过 Component + Container 集成测试
- 与 vernal-context / vernal-expression 集成测试

## 五、风险评估

| 风险 | 影响 | 对策 |
|------|------|------|
| BeanDefinition 字段爆炸 | API 复杂 | 分阶段实现，先核心后字段 |
| Spring 反射机制在 Rust 中无对应 | 性能权衡 | 通过 trait + 闭包替代 |
| BeanPostProcessor 与现有 Container 调度整合 | 破坏现有逻辑 | 在 Container 加 `Vec<Arc<dyn BeanPostProcessor>>`，可空 |
| Aware 体系与生命周期集成 | 递归解析 | 仅作为可选检测，缺失时跳过 |
| PropertyEditor 体系庞大 | 工作量大 | 优先级：基础类型 + 集合；高级的 FileEditor/URL/ClassEditor 按需 |
