## 二、形态不同的 7 个对象（🔶）

### 1. `ApplicationEvent` ↔ 泛型 `Arc<T>`

Java 的事件继承 `ApplicationEvent`，vernal 直接使用泛型 `T: Any + Send + Sync`
发布到 `EventBus`。语义等价：vernal 用类型系统替代继承；vernal 不再需要 `EventObject`
源对象（事件无 source 字段，需要源信息的事件自带字段）。

### 2. `ApplicationListener<E>` ↔ `ApplicationEventListener<E>` trait

Java 通过继承 `ApplicationListener<E>` 实现监听；vernal 通过泛型 trait `ApplicationEventListener<E>`
+ `IoC` 注入实现监听。语义对齐（按事件类型隔离），但 vernal 用 trait 方法 `on_event(&self, Arc<E>)` 替代
Java 的 `onApplicationEvent(E)`。

### 3. `SmartLifecycle` ↔ 合并到 `Lifecycle`

vernal 的 `Lifecycle` trait 同时承载 Spring 的 `Lifecycle` + `SmartLifecycle` +
`Phased` 语义。`is_auto_startup / phase / is_pauseable` 三个钩子默认实现与
Spring 7.0 一致；`stop(callback)` 由 `ManagedTaskSupervisor` 两阶段停机替代。

### 4. `Aware` 系列 ↔ IoC 显式依赖注入

Java 通过 `ApplicationContextAware` / `EnvironmentAware` / `ResourceLoaderAware` /
`MessageSourceAware` / `ApplicationEventPublisherAware` / `ApplicationStartupAware` /
`EmbeddedValueResolverAware` / `LoadTimeWeaverAware` 等统一注入外部依赖；vernal 走
`resolver.resolve::<T>()` 直接依赖注入，**没有 Aware 系列**。这是设计层面的形态差异，
不是缺失。

### 5. `ConversionService` ↔ `T: FromStr`

Java 用反射 `ConversionService` 支持任意类型转换；vernal 用 Rust 标准库 `FromStr` +
`ConfigurationProperties::bind` 提供类型安全绑定。Spring 的转换表由运行期决定；
vernal 由 trait bound 在编译期决定。

### 6. `ApplicationContextAwareProcessor` ↔ 不实现

Java 的 `ApplicationContextAwareProcessor` 在 bean 创建时通过反射注入；
vernal 通过 IoC 显式依赖注入，不需要运行期处理器。

### 7. `EventPublicationInterceptor` ↔ AOP 透明处理

Java 通过 `EventPublicationInterceptor` 在方法返回时自动发布事件；
vernal 由业务代码显式调用 `EventBus::publish` 或由 `vernal-aop` 拦截器封装。
两者语义等价，但调用方式不同。

## 五、业务逻辑一致性检查

### ✅ 完全一致的逻辑

- **refresh / start / close 状态机**：vernal 与 Spring 完全对齐（9 态：Created /
  Refreshing / Refreshed / Starting / Ready / RollingBack / Draining / Failed /
  Closed）；状态推进由公开方法保证，不依赖 boolean 推断
- **事件多播**：vernal 用 `tokio::sync::broadcast` 实现泛型 `Arc<T>` 多播；
  订阅者 lagged 语义与 Spring `SimpleApplicationEventMulticaster` 一致
- **属性优先级 + Profile + 占位符**：`ApplicationEnvironment` 与 Spring Environment
  语义完全一致：高优先级来源先返回、`${key:default}` 占位符、Active-over-Default
  Profile、循环检测、深度上限
- **条件装配 AND 语义**：多条件同时命中才纳入，与 Spring 一致
- **AOP Advisor Order**：vernal 与 Spring 一样按 order 升序排序拦截器
- **类型安全配置绑定**：`ConfigurationProperties::bind` 在编译期确定字段类型，
  运行时按字段精确读取属性；与 spring-boot @ConfigurationProperties 等价
- **后台任务两阶段停机**：`ManagedTaskSupervisor` 先 graceful timeout，再 abort timeout；
  与 tx_di `App::shutdown` 的优雅等待 + 强制终止语义一致
- **跨平台信号监听**：vernal 监听 Ctrl-C / SIGTERM / SIGHUP / Windows Break /
  Close / Shutdown，发布 `ApplicationShutdownSignal` 事件，再取消应用；与 JVM
  shutdown hook 等价

### ⚠️ 部分一致的逻辑

- **Aware 注入系列**：vernal 走 IoC 显式依赖注入，**不实现** Aware；用户需手动
  `resolver.resolve::<ApplicationContext>()` 获取
- **Lifecycle phase**：vernal 用 IoC 依赖计划排序 + 启动期 `init_sort`，
  **不引入** Spring 的 phase 数值（Integer.MIN_VALUE → Integer.MAX_VALUE）；语义等价
  但实现路径不同
- **`stop(callback)`**：vernal 的 `Lifecycle::stop` 是异步签名，不接受回调；
  两阶段停机由 `ManagedTaskSupervisor` 独立完成，语义等价
- **AOP 拦截时机**：vernal 由过程宏 + 显式 `#[intercept]` 织入，运行期没有
  `BeanPostProcessor` 后置处理
- **启动埋点**：vernal 的 `StartupReport` 是聚合报告，**不是** 实时步骤流；
  与 spring-boot StartupEndpoint（`BufferingApplicationStartup` 缓冲模式）等价

### ❌ 未实现的逻辑

- **父子 ApplicationContext**（HierarchicalBeanFactory）：vernal 暂不支持父子 Context；
  多 Context 通过独立 `Arc<ApplicationContext>` 隔离
- **Aware 注入系列**：vernal 走 IoC 显式依赖注入
- **XML 配置**：vernal 不支持 XML 加载 / 解析
- **ClassPath 扫描**：vernal 不扫描包路径，由过程宏 `#[derive(Component)]` 编译期收集
- **ConversionService**：vernal 用 `T: FromStr`，不支持任意目标类型反射转换
- **i18n**：vernal-context 不实现 MessageSource / LocaleContext；如需 i18n，
  走独立 `vernal-i18n` 子 crate
- **AOT processing**：vernal 由 `ComponentDefinition` 静态描述符替代 `ContextAotProcessor`
- **LoadTimeWeaver**：vernal 不实现类加载期编织；AOP 由过程宏静态编织
