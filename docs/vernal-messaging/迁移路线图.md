# vernal-messaging 全量迁移路线图

> 版本：v2.0（2026-07-27）｜基线：Spring Framework 7.0.8 `spring-messaging`
> 适用范围：`docs/vernal-messaging` 四文档；本文是实施顺序与门禁，不代表当前代码已完成。

## 一、总目标与不可违背的边界

目标是实现 `spring-messaging` 的**可观察功能语义完全迁移**：消息模型、通道、拦截器、处理器调用、转换、模板、路由、注解/映射、STOMP、RSocket、TCP、Reactive 调用模型及其测试 oracle 均必须有 Rust 承载方案。允许 Rust 化、feature 拆分或独立 crate，但不能以“协议专属”“Reactor 专属”作为永久排除理由。

`vernal-messaging` 只承载 Spring Messaging 的框架中立核心，不依赖 `ddd4r`。ddd4r 适配放在外部建议 crate `ddd4r-vernal-messaging`，由该 crate 同时承担类型适配、生命周期接入及领域语义映射。

```text
vernal-messaging-core（无 ddd4r 依赖）
  ├─ Message / Headers / Builder
  ├─ MessageChannel / SubscribableChannel / PollableChannel
  ├─ MessageHandler / Converter / Template / Routing
  ├─ STOMP、RSocket、TCP、Reactive feature 或 companion crate
  └─ 用户可观察语义与测试 oracle
             ▲
ddd4r-vernal-messaging（外部集成）
  ├─ MqEvent、Publisher、Handler 的显式适配
  ├─ Acknowledgment 的独立确认语义
  └─ ConsumerEngine 的消费运行时适配
             ▲
ddd4r-mq-* / ddd4j 兼容层
```

重要语义边界：`Acknowledgment` 是消费确认/重投/拒绝协议，不等于 `ChannelInterceptor`；`MessagePublisher` 只有发布能力，不天然是 `SubscribableChannel`；`ConsumerEngine` 是 broker 消费运行时，不属于 `vernal-messaging` 核心。

## 三、实施原则

1. 先定义用户可观察合同，再选择 trait、宏、异步运行时或协议 crate。
2. 核心 crate 的 `Cargo.toml` 不出现 `ddd4r-*`；桥接只能由外部 crate 反向依赖两侧。
3. Rust 类型可合并实现文件，但对象级清单必须逐项记录：独立实现、语义合并、feature 实现或 companion crate。
4. 每个 Spring 行为至少有一个测试 oracle；协议、Reactive 和模板体系不能用“暂不迁移”结案。
5. Java 反射/注解可改用注册表、闭包、过程宏，但必须保留调用选择、参数绑定、异常和返回值可观察结果。

## 四、阶段验收重点

### S1-S7 核心与编程模型

覆盖消息标识、时间戳、content type、reply/error channel、header accessor、send timeout、订阅顺序、拦截器回调、handler 异常、转换协商、request-reply、目的地模式及映射注册。`ReactiveMessageHandler` 不是把 reactive 删除，而是 S8 的异步语义入口。

### S8-S11 协议与 Reactive

按 feature 组织可选实现，例如 `stomp`、`rsocket`、`tcp`、`reactive`；也可分别建立 `vernal-stomp`、`vernal-rsocket`、`vernal-messaging-tcp`、`vernal-messaging-reactive`。无论组织方式如何，公共消息/处理/错误/拦截合同必须复用核心，协议行为要通过端到端 oracle 验证。

### S12 ddd4r 外部集成

建议 crate：`ddd4r-vernal-messaging`。它定义 `MqEvent ↔ Message`、`MessagePublisher ↔` 明确的发送适配器、`MessageHandler ↔ DeliveryHandler`、`Acknowledgment ↔ SettlementPort`、`ConsumerEngine ↔ RuntimeSupervisor`。不得把确认伪装成拦截器完成回调，不得把发布器包装成订阅通道，不得把 ConsumerEngine 注册进核心。

## 五、测试 oracle 与发布门禁

| 维度 | 必须观察 |
|---|---|
| 消息 | payload、headers、ID/timestamp、复制/覆盖、错误携带原消息 |
| 通道 | 返回值、超时、投递顺序、订阅退订、并发可见性 |
| 拦截器 | pre/post/after 的触发条件、顺序、短路与异常 |
| 处理器 | 参数来源、返回值路由、同步/异步、取消与异常链 |
| 转换/模板 | content type、hint、失败类型、目标解析、request-reply |
| Reactive | demand、backpressure、cancel、error、complete |
| STOMP/RSocket/TCP | frame/metadata、连接/session、协议错误、关闭与重连 |
| ddd4r | 发布 receipt、消费 delivery、Ack/Nack/Requeue、幂等、生命周期 |

发布必须通过 `cargo test --workspace`、各 feature 的 `cargo test --all-features`、协议互操作测试、文档示例编译测试和名称/统计一致性检查。

## 六、ddd4j/ddd4r 整合边界

ddd4j 的消息头、事件信封、确认、路由表达式是外部生态的输入，不改变 Spring Messaging 核心定义。ddd4r 可提供适配器和 oracle，但不能成为核心 trait 的前置依赖。领域事件可在桥接层编码为 Message，broker delivery 可在桥接层还原；确认与通道发送完成分别记录，避免语义混淆。

## 七、技术债与风险

| 风险 | 处置 |
|---|---|
| 协议功能被错误排除 | S8-S11 为强制阶段，必须有 feature/独立 crate 交付 |
| Reactive 被同步 Future 掩盖 | 单独定义 demand/cancel/error/completion oracle |
| 核心反向依赖 ddd4r | CI 检查依赖图，`vernal-messaging` 禁止 ddd4r 字符串依赖 |
| Ack 与 interceptor 混淆 | 使用独立 `SettlementPort`/`AcknowledgmentAdapter` 并测试状态机 |
| Publisher 被当作订阅通道 | 仅实现发送适配；订阅必须有独立消费端口 |
| 统计漂移 | 四文档共同采用同一基线、状态图例和对象计数 |

## 八、完成定义

完成 S13 后，`vernal-messaging` 及其 companion crates 覆盖 Spring 7.0.8 `spring-messaging` 的公共和协议可观察语义；Rust 化差异、feature 边界、未实现项及兼容限制均有明确记录和测试。`ddd4r-vernal-messaging` 可选接入，不改变核心 crate 的独立可用性。
